# 同步链路修复记录（2026-07-27 ~ 07-29）

起因：微信与 QQ 同步都失效，微信停在 2026-05-14，QQ 停在 2026-05-14。Telegram 正常。

## 一、微信：wx-cli 输出结构变更

`wx` CLI 升级后把 JSON 结果包进了外层对象，而 `wechat.py` 三处 `json.loads` 仍按裸数组迭代，取到的是 dict 的 key（字符串），于是 `session.get(...)` 抛 `AttributeError: 'str' object has no attribute 'get'`。异常抛在 `sync_sessions` 的 try 之外，直接冒到 `_run_sync_all`，界面显示「微信失败」。

| 命令 | 现在返回 | 原代码假设 |
|---|---|---|
| `wx sessions` | `{meta, sessions: [...]}` | 裸数组 |
| `wx history` | `{chat, count, messages: [...], meta, …}` | 裸数组 |
| `wx new-messages` | `{count, messages: [...]}` | 裸数组 |

**改动**：新增 `_rows(raw, key)`，新旧两种格式都兼容，三个调用点各改一行。

**附带修复**：`sync_new_messages` 从不写 `sync_state`，导致增量同步成功后 `/api/sync/health` 的 `last_sync` 仍停在上次全量同步时间 —— 同步成功却显示成没同步。现按 `chat_id` 记录批次内最大时间戳后写回，且**只向前推进**（`MAX(excluded, COALESCE(现值, excluded))`），避免把全量同步留下的更新检查点改小。

## 二、QQ：四层故障叠加

### 1. Docker daemon 损坏

所有 docker API 返回 500（版本协商失败），NapCat 容器不在，但 `com.docker.backend` 仍占着 `127.0.0.1:40653` 的端口转发 —— TCP 连得上、无人应答，客户端干等 120s 超时。重启 Docker Desktop 后恢复。

### 2. NapCat 登录态失效

`快速登录错误：登录态已失效`，需扫码。扫码入口：`http://127.0.0.1:6099/webui?token=<WebUI Token>`（二维码自动刷新，比命令行里那张更可靠）。

### 3. QCE token 取错了地方 → 403

`qq_launcher._tail_logs` 靠正则刮容器日志里的 `[QCE] Token:` 行，但该行打的是**轮换前的旧值**（实测 15 次启动全打旧值），拿去请求得到 `403 INVALID_TOKEN`。

诊断要点：无凭据是 `401 MISSING_TOKEN`，带旧 token 是 `403 INVALID_TOKEN` —— 传输方式没问题，是值被拒。

**权威来源是 `~/.chat-analyzer/qq-stack/qce-data/security.json` 的 `accessToken`。**

**改动**：新增 `_token_from_disk()`，`_persist_token()` 改为文件优先、日志兜底；`start()` 挂 `_watch_token_file()`（QCE 启动后才写该文件，值还可能在启动过程中轮换，盯 120s）。

### 4. QCE v6 与当前 NapCat 不兼容

安装器固定拉 `releases/latest`，装上了 v6.1.7，运行模型完全变了：

| | v5.x | v6.x |
|---|---|---|
| 形态 | Node 应用，zip 自带 `node_modules` | 预编译二进制 |
| `dependencies` | 一批 npm 包 | `{}` |
| 实际服务 | node 进程 | `bin/linux-x64/qce-server`（22 MB）+ `runtime/rustBridge.mjs` |
| 数据目录 | `/app/.qq-chat-exporter` | `/root/.qq-chat-exporter` |

镜像里的 NapCat.Core 4.18.1 加载不起 v6 插件（无任何日志，`PluginManager` 不动），且 v6 要求 `NapCat bridge: 127.0.0.1:40654`、数据目录也与 compose 挂载点不符。

**改动**：`QCE_PINNED_VERSION = "v5.5.79"`，`_fetch_latest_release()` 支持按 tag 取 release（置 `None` 即恢复跟随 latest）。

### 5. 解压丢执行位

`zipfile.extractall()` 不保留 Unix 权限位。v5 是纯 JS 所以从未暴露；v6 带二进制才踩到 —— zip 里存的是 `0o100755`，落地成 `-rw-r--r--`，插件无法执行它。

**改动**：`_extract_all()` 解压后按 zip 存的 mode 补回权限位，两个解压点都改用它。

### 6. 安装时删掉了正在运行的插件

旧实现先 `rmtree` 目标目录再下载解压，运行中的 QCE 在这段窗口里丢文件 —— GET 照常（不读请求体），按需 `require` 的 POST 全部 500（`Cannot find module '../encodings'`）。

**改动**：解压到 `.staged` → 备好完整目录 → `rename` 换入（旧目录先改名 `.retired` 再删）。窗口从整个下载解压过程缩短到两次 `rename`。返回值新增 `restart_required`（原子切换只影响尚未加载的模块，运行中实例仍是旧版）。

**验证**：强制重装 v5.5.79（44 MB / 16.1s）期间每秒探测 `POST /api/messages/fetch`，148 次全部 200，零中断。

## 三、QQ 深度翻页断连与回补机制

QCE 在**单会话连续翻页约二十几页后断开连接**（实测：第 28 页 `ReadError`，累计 5400 条 / 153s）。换 batchSize/limit 无效；25 个会话 A/B（无间隔 vs 间隔 0.5s）均 25/25 成功 —— 与请求节奏无关，只与单会话翻页深度有关。

原实现下这是**死锁**：第 28 页断连 → 异常抛出 → 前 27 页的检查点全部丢弃 → 下次仍从 page 1 开始 → 又在二十几页处断 → 消息多的会话永远追不上。

### 改动

`sync_one_chat` 拆成两阶段（`page 1` 是最新，页码越大越旧）：

1. **增量**：`page 1` 起往旧翻，撞到上次水位线即止。从最新一条连续翻下来，水位线可安全推进。
2. **回补**：增量段翻完后，接着上轮断掉的页继续往更旧翻。

- `_walk_pages` 捕获 `TRANSIENT_ERRORS`（连接层）不再抛出，已取回的页连进度一起留下；单轮上限 `PAGES_PER_RUN = 20` 页。
- 新增 `sync_state.backfill_page` 记录断点，`NULL` = 该会话历史已翻到底。
- **断点只前进或清空**：`max(resume or 1, last_page + 1)`。第一版写成 `max(last_page + 1, 1)`，增量段首页断连时 `last_page` 为 0，会把已推进到的页码覆盖成 1，回补进度清零（实测第 3 轮 `33 → 1`）。
- HTTP 状态错误（403/500）不在 `TRANSIENT_ERRORS` 内，照旧冒泡记 `skipped` —— 否则 token 一失效，全部会话会伪装成「旧历史没翻完」，把真故障藏起来。

### 重试退避

`_get`/`_post` 合并为 `_request`，退避 `(1s, 3s, 7s)`、最多 4 次尝试。断连后 QCE 需要几秒恢复，原来立即重试 3 次等于连撞三下就放弃（实测有整轮 5 秒内全败、断点零推进）。403 不重试，直接抛出。

### 每会话独立事务

失败会话 `rollback()` 掉自己的半截写入，不再留给下一个会话的 `commit` 顺带提交 —— 那是「任务报 6 条、库里 +51」计数错位的原因。

## 四、上报缺陷（掩盖了整个故障）

`run_qq_sync` 拼消息时只取 `imported` 和 `chats`，把 `skipped` 丢掉。**185 个会话全部失败**时显示为「同步完成: 0 条消息 (0 个聊天)」，与「没有聊天要同步」完全一样，导致早期排查方向被误导。

**改动**：

- 消息中列出 `skipped` 数量与头几个失败类型
- 全部会话被跳过时状态判为 `error`，不再报「完成」
- `pending`（旧历史未翻完，正常分批推进）与 `skipped`（真失败）分开上报
- `/api/sync/all` 的 QQ 段有同样盲区，一并修正

## 八、排查过程中的可靠性提示

- **`docker logs` 不可用于时序判断**：stdout 与 stderr 是分别有序地拼接，位置上的「最后一行」不是时间上的最后一行；且多行写入的续行不带 Docker 时间戳（本例 24 万行里只有 18 万行能解析出时间戳，且截止在一个月前）。要判断时序必须 `--timestamps` 后按时间戳排序，或者直接查运行状态（端口是否绑定、进程是否存在）。
- **日志行里的 `MM-DD HH:MM:SS` 是消息时间戳，不是日志时间**。
- **探测 QCE 分页深度时 `limit` 必须与同步一致**（同步用 200）—— 页码基准随 `limit` 变化，用 `limit=20` 探出来的页码与存储的断点不可比。
- 任务记录 TTL 为 1 小时（`TASK_TTL_SECONDS`），完成的任务会被清理。要留证据必须在窗口内抓取。
